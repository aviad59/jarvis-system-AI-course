תרגיל 3 · 40 דקות

בונים שרת MCP ליכולת שבחרתם

בחרו צורך קטן מהפרויקט שלכם ובנו עבורו 3–5 כלים. בסוף תחברו לקוח לשרת, תפעילו כל כלי ותבדקו שהתוצאה תואמת למה שהגדרתם.

אתם בוחרים את היכולת ואת מקור המידע. העדיפו מקור שכבר נגיש לכם ופעולות שאפשר להשלים ולבדוק בזמן התרגיל.

נקודת ההתחלה

פתחו את תיקיית exercise-3-fastmcp ב־Claude Code ובמסוף. בתיקייה תמצאו:

  • example_server.py — דוגמה מלאה עם כלי אחד שבודק אם תיאור עבודה כולל כותרת ומטרה.
  • starter.py — קובץ העבודה שלכם. שלוש הפונקציות שבו הן נקודת התחלה לשינוי, ולא כלים גמורים.
  • inspect_server.py — לקוח שמגלה כלים מהשרת שלכם ומאפשר להפעיל כלי עם קובץ קלט.
  • verify_example.py — בדיקה מוכנה של הדוגמה בלבד.

לפני השיעור מכינים Python 3.10 ומעלה וסביבה עם החבילה העצמאית fastmcp==4.0.0. פקודות ההכנה המלאות. בדיקת הדוגמה כבר צריכה לעבוד לפני תחילת 40 הדקות.

בדיקת מוכנות ב־Windows

פתחו PowerShell בתיקיית התרגיל. להכנת הסביבה לפני השיעור הריצו:

py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

לאחר ההכנה הריצו:

.\.venv\Scripts\python.exe verify_example.py

בסיום מופיעה הודעת PASS. היא מאשרת את דוגמת המרצה. את הכלים שלכם תבדקו בהמשך באמצעות inspect_server.py. ב־macOS/Linux השתמשו ב־.venv/bin/python כנתיב ה־Python שלכם.

1. בוחרים צורך ומגדירים כלים · דקות 0–8

נסחו במשפט אחד: מי המשתמש, מה הוא רוצה לבצע ואיזו תוצאה תראו כשזה עובד. למשל, אפשר לעבוד עם מסמכים מקומיים, נתוני תרגול או פונקציות מתוך פרויקט שכבר קיים אצלכם.

בחרו 3–5 פעולות שמשלימות זו את זו. לכל אחת רשמו:

  • שם ותיאור שמסבירים מתי להשתמש בה.
  • מה צריך למסור לה ומה היא תחזיר.
  • דוגמה לקלט תקין והתוצאה הצפויה ממנו.
  • מקרה שבו עליה לדווח על מידע חסר או על שגיאה.

בחרו אם הפעולות צריכות לשמור מידע בין קריאות. לפעולה עצמאית הגדירו בקשה שמכילה את כל המידע הדרוש לה.

מה צריך לראות: רשימה קצרה של 3–5 כלים עם קלט ותוצאה צפויים. אלה הדרישות שינחו את הבנייה.

2. בונים כלי ראשון ואז את השאר · דקות 8–22

פתחו את example_server.py ועקבו אחרי הרצף: יצירת שרת, הפיכת פונקציה לכלי בעזרת @mcp.tool, הגדרת טיפוסים, בדיקת קלט והחזרת תוצאה.

עברו ל־starter.py. החליפו את שמות הפונקציות, החתימות והתיאורים לפי מה שבחרתם. בקשו מ־Claude Code לממש קודם כלי אחד ובדקו אותו, ורק אז המשיכו לשאר.

אפשר לבקש: ״בנה ב־starter.py את הכלים שהגדרנו לצורך שלנו. השתמש ב־FastMCP העצמאי, בטיפוסים ובתיאורים ברורים. בדוק את הקלט והחזר תוצאה שאפשר להשוות למקור. הסבר בעברית מה עושה כל שורת קוד. פעל בתוך המקורות והפעולות שהגדרנו.״

מה צריך לראות: 3–5 פעולות שמבצעות את העבודה שהגדרתם. כל פונקציה מכילה מימוש, וכל תיאור מסביר את הכלי שבניתם.

3. מחברים לקוח וקוראים לכל הכלים · דקות 22–32

הלקוח המצורף מפעיל את השרת שלכם כתהליך מקומי. מריצים את הפקודה הבאה באותו מסוף. מתוך תיקיית התרגיל הריצו:

.\.venv\Scripts\python.exe inspect_server.py --server starter.py

בדקו שברשימה מופיעים כל הכלים שבניתם, עם השמות והתיאורים שלכם.

כדי להבין איך מפעילים כלי, אפשר להריץ פעם אחת את דוגמת המרצה:

.\.venv\Scripts\python.exe inspect_server.py --server example_server.py --tool validate_task_brief --arguments-file example-input.json

עכשיו צרו לכלי שלכם קובץ קלט שמתאים לשדות שהגדרתם. בקשו מ־Claude Code להכין את הקובץ ובדקו את הערכים לפני ההרצה. למשל, אם קראתם לכלי check_item ולקובץ my-input.json, הריצו:

.\.venv\Scripts\python.exe inspect_server.py --server starter.py --tool check_item --arguments-file my-input.json

החליפו את שם הכלי ואת שם הקובץ בדוגמה לשמות שלכם. הריצו קריאה תקינה לכל אחד מהכלים שבניתם והשוו את התוצאה לקלט או למקור.

מה צריך לראות: כל כלי מופיע בקטלוג וכל כלי הופעל בהצלחה דרך לקוח MCP. כך בודקים גם את התקשורת וגם את ביצוע הפונקציה.

4. בודקים כשל ומכינים הדגמה · דקות 32–40

  1. בחרו כלי אחד ובדקו מה קורה כשחסר לו מידע או כשהקלט שגוי. בדקו שהחוסר או השגיאה מוצגים בבירור.
  2. אם החלטתם לשמור מידע, ודאו שאפשר לקרוא אותו בחזרה. בדקו גם מה קורה אחרי הפעלה מחדש של השרת.
  3. שמרו את קובצי הקלט ואת התוצאות. בחרו כלי אחד שתוכלו להדגים לכיתה בתוך דקה: הבקשה, ההפעלה והתוצאה.

תוצאה עסקית כמו valid=false עשויה להיות תשובה נכונה שמצביעה על בעיה בתוכן. שדה חובה שלא נשלח יכול לגרום לשגיאת קלט. הגדירו מראש מה מצופה במקרה שלכם.

סיימתם כאשר

  • אתם יכולים להסביר במשפט איזה צורך השרת פותר.
  • בקטלוג מופיעים 3–5 כלים ממומשים עם תיאורים וקלט ברורים.
  • כל כלי הופעל לפחות פעם אחת דרך לקוח MCP והתוצאה נבדקה.
  • לפחות מקרה אחד של מידע חסר או כשל נבדק והתוצאה ברורה.
  • ברור אם מידע נשמר בין קריאות ומה קורה אחרי הפעלה מחדש.

בהדגמה לכיתה מציגים כלי אחד נבחר. בדיקת הסיום שלכם כוללת את כולם.

אם נתקעתם

השרת ממתין במסוף? בהרצה לבדו הוא מחכה ללקוח; השתמשו ב־inspect_server שמפעיל אותו עבורכם. חסר כלי ברשימה? בדקו את @mcp.tool ואת קובץ השרת שהעברתם לפקודה. הקלט נדחה? השוו את שמות השדות ואת סוגיהם לחתימת הפונקציה. זקוקים לעזרה באיתור תקלה בשרת שלכם? צמצמו לכלי אחד ובדקו את הודעת השגיאה לפני שממשיכים.

כתבו הודעות אבחון ללוגים או ל־stderr; stdout משמש לתקשורת MCP. פרטי הפעלה, לוגים וחיבור ללקוחות נוספים.

לכל סוג מידע יש מקום מוגדר. היסטוריית שיחה מנוהלת ביישום העוזר. נתונים שצריך לשמור מחייבים אחסון מפורש. בפעולה עצמאית העבירו בכל קריאה את המידע הנדרש; במצב מתמשך שמרו וקראו אותו במפורש.

שני בונוסים · אחרי השלמת התרגיל

1. מצב מתמשך ושחזור

הוסיפו תהליך שיוצר טיוטה עם מזהה ושומר אותה בקובץ. הפעילו מחדש את השרת וקראו את הטיוטה לפי המזהה. הגדירו היכן מותר לשמור ומה קורה כשמבקשים מזהה חסר.

2. כשל וניסיון חוזר

דמו כשל אחרי פעולה מקומית ולפני החזרת תשובתה. הוסיפו מזהה פעולה ובדיקה של תוצאה קיימת כך שניסיון חוזר יחזיר את התוצאה שכבר נוצרה. בדקו גם מה קורה כאשר נשלח תוכן שונה עם אותו מזהה.
