בנו Vault (כספת) של מסמכי הצוות

מטרת התרגיל: להפוך חומרי פגישות למסמכים שאדם וסוכן יכולים לקרוא, לקשר ולבדוק. Vault (כספת) הוא המונח הרשמי של Obsidian לתיקייה מקומית עם פתקים והגדרות; אפשר לתת לו את השם ״מסמכי הצוות״.

אתם בונים תיקייה ופתקים משלכם בעזרת Obsidian ו־Claude Code עם filesystem MCP. לא מעתיקים Vault גמור. אין צורך ב־Skill או בבניית שרת MCP חדש בשלב זה. לאחר כתיבת הפתקים מחברים אותם ל־RAG הקיים, מעדכנים את האינדקס ובודקים את אותו Jarvis מהשבוע הקודם. משתמשים בחשבון ובסביבה שהוכנו לכיתה; ההוראות כאן לא הפעילו שירות או התקינו חבילה.

  • כרטיס הפרויקט: מטרת הפרויקט, הקשר עסקי/טכני, מה עדיין לא ידוע וקישורים לשתי הפגישות.

  • טיוטה: מסמך קצר שמסומן Draft וכולל שאלה או נוסח שממתין לאישור. אין לנסח ״התקלה נפתרה״ כעובדה.
  • תחום אינדוקס עתידי: indexing-scope.md מציין לכלול רק Projects ו־Meetings ולהחריג Drafts, Templates, .obsidian ותוצרים שנוצרו.

חיבור filesystem MCP — לאחר דמו המרצה

סביבת Node/npx וחבילת השרת חייבות להיות מוכנות ונבדקות מראש. npx עשוי להוריד חבילה אם אינה קיימת; לא מתחילים הורדות בהפתעה באמצע התרגיל. זו פקודת ההכנה הרלוונטית ב־macOS/Linux; יש להחליף את הנתיב בתיקייה החדשה שלכם.

cd "/absolute/path/to/Team-notes"
claude mcp add --transport stdio --scope project team-files -- npx -y @modelcontextprotocol/server-filesystem "$PWD"
claude

בתוך Claude Code: /mcp. מוודאים שהשרת מחובר, ואז מבקשים דרך team-files להפעיל list_allowed_directories. התוצאה צריכה להתאים לתיקיית התרגול שלכם. אין להסתפק בהודעת ״נוספה תצורה״ כהוכחה שהשרת פועל.

Roots חשובים: השרת יכול לקבל נתיבים בשורת הפקודה, אבל Roots מהלקוח מחליפים אותם. Claude Code שולח את תיקיית הפתיחה ותיקיות נוספות שהוגדרו. לכן מתחילים מתוך ה־Vault, לא משורש כל הקורס, ולא מוסיפים תיקיות ב־--add-dir או /add-dir. אם מופיע תחום רחב מהמתוכנן, עוצרים ומתקנים את החיבור לפני בקשת עריכה.

מחבר הקבצים קורא וכותב Markdown ישירות. אין צורך להתקין Obsidian REST plugin. הרשאת מחבר לתיקיית האב יכולה לכלול גם Drafts; ההחרגה של Drafts מאינדוקס RAG היא כלל אחר, ואינה איסור קריאה של מחבר filesystem.

דרך team-files, הצג את התיקיות המותרות ואת רשימת הקבצים.
אני בונה Vault חדש מתוך חומרי פגישות סינתטיים שבחרתי. הצע מבנה לפי הדרישות,
והצע טקסט קצר לכרטיס הפרויקט. אל תוסיף תוצאות בדיקה או סגירת תקלה.

אחרי שבדקתי את ההצעה, צור את הקבצים שאישרתי.
בכל פגישה הפרד בין מה שנרשם, החלטות, פעולה ובעלים, ומה שלא ידוע.
אל תעתיק Vault פתרון מוכן ואל תערוך קבצים מחוץ לתיקיית התרגול.

קרא בחזרה את שני הפתקים דרך team-files.

התאימו את הבקשה לתוצר שלכם במקום לשלוח אותה אוטומטית כפי שהיא. אין צורך לשנות את מצב המשימות או לקרוא את כלי התקלה בתרגיל הזה. כן צריך להשלים את מסלול RAG ו־Jarvis המתואר בהמשך.

Properties: מה אופציונלי באפליקציה ומה חובה כאן

אפשר לכתוב פתק Obsidian ללא properties. לצורך מתאם הקורס שמגיע בהמשך, על כרטיס הפרויקט ועל שתי הפגישות להוסיף שדה project_id עם אותו מזהה פרויקט שבחרתם. לשתי הפגישות מוסיפים גם meeting_date עם תאריך הפגישה המדויק. שם שדה זה הוא מוסכמה של המתאם שלנו.

---
project_id: MY-PROJECT
meeting_date: 2026-11-09
---

התאריך בדוגמה אינו דרישה: בכל פתק כותבים את תאריך הפגישה שתיעדתם. בכרטיס הפרויקט אין צורך להוסיף תאריך פגישה. אפשר להשתמש בממשק Properties של Obsidian או ב־frontmatter הזה בראש הקובץ. המתאם הצר תומך בשדות סקלריים; אין צורך ברשימות YAML, plugins או שדות מסובכים.

הוספת properties אינה מחליפה תאריך וכותרת ברורים לאדם. אל תשתמשו בתאריך יצירת הקובץ במקום בתאריך הפגישה.

בדיקת הצלחה — על הקבצים שיצרתם

  1. Obsidian פותח את ה־Vault החדש ומציג את כל ששת קובצי התוצר.
  2. כל קובץ צפוי קיים בנתיב הנכון; שני פתקים מכילים תוכן אמיתי שונה ולא רק תבנית.
  3. קורא אחר יכול למצוא את מטרת הפרויקט, מי אחראי לפעולה ומה לא ידוע.
  4. שני הקישורים מכרטיס הפרויקט פותחים את הפגישות הנכונות. לדוגמה: [[Meetings/meeting-1]].
  5. כל פתק מבדיל בין דיווח, החלטה ופעולת המשך, ומשאיר מידע חסר גלוי.
  6. לא נכתבה מסקנה שאינה נתמכת במידע שתיעדתם.
  7. properties הנדרשים קיימים, ותחום האינדוקס העתידי מחריג טיוטות ותצורה.
  8. דרך MCP אפשר לקרוא בחזרה אחד הקבצים; מתעדים אם החיבור לא פעל, בלי לסמן זאת כהצלחה.

חובה לעדכן את האינדקס של ה־RAG הקיים ולבדוק את אותו Jarvis על המקור החדש. אין צורך ב־Skill. Obsidian שמציג עריכה אינו מעדכן את אינדקס ה־RAG אוטומטית.

שני מסלולים שונים: בזמן הבנייה ובזמן השאלה

בנייה: המשתתפים ו־Claude Code יוצרים/עורכים קובצי Vault דרך filesystem MCP ומתאימים את הקוד הקיים. לצורך עריכת מאגר הקוד המקורי עשוי להידרש תחום קבצים נוסף; לא מרחיבים את שרת הדמו בלי לבדוק Roots ותחום הרשאות. אפשר לבצע שינויי קוד מתוך סביבת המאגר הקיימת ולהשאיר את מחבר הדמו נפרד.

Runtime: אותו Jarvis → אותו RAG → האינדקס שנבנה מקובצי ה־Vault → מקטעים עם מקור → תשובה וציטוט. Obsidian הוא מקור קבצים, לא database; האינדקס הוא תוצר חיפוש נפרד.

חיבור filesystem MCP ל־Claude Code אינו הוכחה ש־Jarvis עצמו משתמש ב־MCP. התרגיל אינו מוסיף לולאת כלים ל־Jarvis, ואינו מציג את ה־MCP של זמן הבנייה כחיבור runtime.

בקשה להתאמת ה־RAG במאגר האמיתי שלכם

אני רוצה להרחיב את אותו Jarvis/RAG שבו השתמשתי בשבוע הקודם.
לפני שינוי, קרא את קובצי ההפעלה והאינדוקס במאגר הזה.
הצג את פקודת ההפעלה הקיימת, את פונקציית קריאת המסמכים,
את המקום שבו נקבע נתיב המקורות ואת האינדקס שהחיפוש באמת קורא.

התאם את קריאת המסמכים ל־Vault שיצרתי, בנתיב שאספק.
קרא רק Meetings ו־Projects; החרג Drafts, Templates, .obsidian ותוצרים.
שמור path, כותרת מקטע, meeting_date ו־project_id ליד הטקסט.
מחזר את chunking, embeddings והדירוג הקיימים; אל תבנה אפליקציה חדשה.
העבר את התצורה לאורך אותו מסלול שה־Jarvis הקיים מפעיל.
אל תניח ששינוי loader לבדו משנה את ה־index שה־runtime קורא.

הראה diff ופקודות מדויקות של המאגר שלי לרענון אינדקס ולהפעלת אותו Jarvis.
הפעל רק את המסלול המקומי שהוכן לכיתה; אל תתקין או תוריד מודלים.
אמת שקטע מהפתק החדש נמצא באינדקס עם מקור לפני שאשאל את Jarvis.

המתאם המוכן ב־workshop יכול לשמש עזר לקריאה ולהשוואה. הוא יוצר אינדקס במבנה של הסדנה; אין להניח שהמבנה הזה מתאים אוטומטית לאינדקס של Jarvis. היעד הוא המאגר שלכם, עם בדיקת החוזה שלו.

איך מוודאים שבאמת השתמשנו בפתק החדש?

בחרו קוד בדיקה ייחודי לצוות, כגון ״שם בדיקת הכיתה: אורן־צוות־7״, וכתבו אותו בפתק אחד בלבד. זהו פרט סינתטי שאתם מוסיפים לצורך בדיקת מקור, ולא טענה על התקלה. אל תכניסו אותו לשאלה או להיסטוריית Jarvis.

  1. שאלו: ״מה שם בדיקת הכיתה שתועד בפגישה האחרונה? ציין מקור״.
  2. בדקו שהתשובה מכילה את הערך מהפתק, ושהציטוט מצביע על הפתק והמקטע המתאימים.
  3. שנו את הערך בקובץ. בלי עדכון אינדקס אין לצפות שה־RAG יראה אותו. הריצו עדכון מפורש ושאלו שוב בשיחה נקייה.
  4. בדקו שהערך החדש מופיע והמקור עדיין נכון. אם הוחזר fixture או replay, ציינו זאת; הוא אינו מוכיח אחזור סמנטי חי.

העתקת הפתק לשאלה, פתיחת הקובץ ישירות ב־Claude Code או תשובת סוכן הבנייה אינם הוכחה ש־Jarvis מחובר למקור.

פקודת בסיס מאומתת — ומה עדיין צריך לבדוק

במאגר הציבורי שנבדק, מדריך Jarvis מפעיל מתוך שורש המאגר:

python jarvis/server.py

זוהי פקודה שקראנו במאגר, לא טענה שהורצה כאן. קודם מאמתים שזה אותו מאגר/ענף של המשתתף ושסביבת Python שלו הוכנה. בקוד שנבדק RagSkill מפעיל rag.build_steps, עם skip_index כברירת מחדל ונתיב index קבוע. לכן צריך להתאים את מסלול המקור והאינדקס, ולא רק לכבות את Skip indexing ולצפות ש־Vault רגיל יעבוד.

המסלול המקומי הזמין בקורס, Session4/complete-rag-agent/agent.py, תומך ב־--documents, --provider ו־--output-dir. זו חלופת reference ללא ממשק Jarvis, לא ״אותו Jarvis״. גם ה־loader שלו דורש metadata של הקורס, ולכן פתק Vault רגיל אינו קלט מוכן ללא התאמה.

cd "/Users/nurit/AI Agents Course/Session4/complete-rag-agent"
python3 agent.py --provider ollama --documents "/absolute/path/to/ADAPTED-course-documents" --generation-model gemma3:4b --output-dir build/vault-demo --question "מה שם בדיקת הכיתה שתועד בפגישה האחרונה?"

ADAPTED-course-documents הוא נתיב לנתונים שהותאמו לחוזה ה־loader, לא ה־Vault הגולמי. מאמתים את המודל המותקן לפני הפעלה. הפקודה נבדקה מול קוד argparse בלבד ולא הורצה במחקר זה. שימוש ב־reference מועיל לאבחון, אך אינו עומד לבדו בדרישת ״אותו Jarvis״.

שני בונוסים מתקדמים — מחוץ ל־40 הדקות

בונוס 1: תשובה שמחברת שלושה פתקים

פזרו מידע הדרוש לתשובה אחת בין שלושה פתקים: מטרת הפרויקט, ההחלטה שהתקבלה ותנאי לביצועה. נסחו שאלה שאף פתק אינו מספיק כדי לענות עליה לבדו. בקשו מאותו Jarvis תשובה משולבת ומקור לכל חלק.

בדיקת הצלחה: התשובה כוללת את שלושת חלקי המידע, מקשרת ביניהם נכון ומפנה לקטע המתאים בכל פתק. הסירו אחד מהפתקים ממאגר החיפוש והריצו שוב: המידע החסר צריך להישאר חסר, בלי השלמה מומצאת. שמרו שאלה, תשובה צפויה ומקורות לבדיקה.

בונוס 2: איזו החלטה עדיין בתוקף?

צרו פתק עם החלטה ישנה ופתק מתאריך מאוחר יותר שמבטל או מחליף אותה במפורש. השאירו את שני הפתקים במאגר ושאלו את Jarvis מה ההחלטה שבתוקף ומדוע.

בדיקת הצלחה: התשובה מזהה את ההחלטה החדשה, מסבירה איזו החלטה היא מחליפה ומצרפת את שני המקורות ואת תאריכיהם. שינוי התאריך לבדו אינו הוכחת ביטול: אם אין הוראת החלפה מפורשת, על העוזר לציין את אי־הוודאות. אין בבונוסים חיבור לאפליקציות או יצירת משימות.

Windows · PowerShell — תיקיית הכספת

פתחו PowerShell בתוך תיקיית הכספת החדשה לאחר הכנת Node, npx ו־Claude Code.

claude mcp add --transport stdio --scope project team-files -- npx -y @modelcontextprotocol/server-filesystem "$($PWD.Path)"
claude

פתחו /mcp ובקשו list_allowed_directories דרך team-files. השוו את הנתיב לכספת שלכם. לעריכת קוד Jarvis פתחו חלון Claude Code נוסף בתוך מאגר Jarvis ומסרו לו את נתיב הכספת כמקור לקריאה.
